## 信息如何分工

- **现有能力**：工具手册依据代码与参数定义描述；新增工具先进入注册表，再同步手册。
- **目标和规范**：需求、设计、交互描述后续变更应遵守的目标。未达成的目标不能写成“已验收”。
- **验证证据**：验证记录只记实际执行过的检查，必须说明日期、环境和未覆盖范围。
- **历史材料**：[历史目录](history/README.md)保留早期验收原始背景，不能据此推断当前构建、线上状态或全部浏览器兼容性。
- **视觉参考**：[概念图](design/devkit-web-concept.png)不是截图、运行数据或功能验收证据；[历史截图](verification/)只作对应阶段的参考。

文档优先级：用户最新明确要求 > 当前产品范围 > 交互与设计约定 > 代码与格式约定。发现代码与文档冲突时记录具体差异并确认当前行为，不能自行把目标改成已完成状态。

## 维护方式

所有用户可见能力变化都应在同次修改中更新对应文档；不要仅在旧文档末尾追加一段覆盖前文。流程、同步矩阵和新工具文档模板见[开发指南](development.md)。`pnpm docs:check` 校验文档链接、工具登记及模式说明的一致性；通过检查仍需人工核对功能语义与限制。
